# Закупки по дефициту и журнал событий

## Закупки

Страница `/procurement` доступна ролям admin, warehouse, manager и finance.
Пункт «Закупки» находится в основной навигации.

Для каждого материала активных производственных планов рассчитывается:

```
к закупке = max(сумма потребностей активных планов − текущий складской остаток, 0)
```

Остаток вычитается один раз из общей потребности, а не отдельно для каждого плана.
Используются существующие рассчитанные потребности планов, включая раскрытие
полуфабрикатов. Завершённые, отменённые и черновые планы в закупки не входят.
После проведения складского прихода дефицит уменьшается. При повторном открытии
страницы и возвращении фокуса данные запрашиваются заново; есть ручное обновление.

Показаны материал, единица, потребность, остаток, количество к закупке, текущая цена,
ориентировочная сумма, ближайший срок плана, число активных планов и ссылка из
карточки материала. Архивные материалы с существующей потребностью не скрываются:
таблица помечает их и предлагает проверить перед закупкой.

Поиск фильтрует материалы по названию. Итоги относятся ко всему результату поиска.
Стоимость рассчитывается десятичной арифметикой и округляется до копеек отдельно
для каждой позиции. Если цена отсутствует, сумма позиции остаётся неизвестной;
интерфейс отдельно показывает число таких позиций и сумму только по известным ценам.

«Скачать закупки Excel» выгружает все строки текущего поиска, независимо от страницы
таблицы. В XLSX используются числовые ячейки количества и денег, ячейки дат,
закреплённая шапка и автофильтр. Неизвестные цены и суммы остаются пустыми.
Максимум — 100 000 позиций; больший результат требует сузить поиск.
Формирование XLSX вынесено из потока event loop. Скачивание передаёт cookie сессии.

Это список потребностей к закупке. Он не создаёт заказы поставщикам, не резервирует
ожидаемые поставки и сам не проводит складские поступления.

API:

- `GET /api/v1/procurement?page=1&page_size=20&search=...`
- `GET /api/v1/exports/procurement.xlsx?search=...`

## Журнал

Страница `/audit` и `GET /api/v1/audit-events` доступны только admin.
В меню администратора есть пункт «Журнал». Доступны поиск по пользователю, объекту,
ID объекта/запроса, фильтр типа события, период, пагинация и подробности.
При переходе между страницами сохраняется верхний ID списка (`through_id`), чтобы
новые события с большими ID не сдвигали просматриваемые записи. «Обновить» сбрасывает
эту границу и возвращает к первой странице.

В PostgreSQL хранится таблица `audit_events`:

- **Изменения данных:** INSERT, UPDATE и DELETE всех существующих бизнес-таблиц,
  включая массовые SQL-операции, складские движения, планы, техпроцессы, зарплату,
  финансы, инструкции, учётные записи и сессии. Сохраняются полные JSON-снимки строки
  до и после изменения, тип операции, таблица, ID, время, автор и ID запроса.
- **События API:** метод, шаблон маршрута, HTTP-статус, время, пользователь и ID
  запроса. В том числе входы, неудачные попытки входа, выходы, экспорты, ошибки и чтение.
  Неизвестные маршруты записываются как `unmatched`. Скачивания `/media` и health-check
  не входят в журнал обращений API.
- **CLI:** изменения учётных записей отмечаются `cli:<пользователь ОС>`.
  Изменения напрямую в БД без контекста приложения отмечаются `system`.
  Неуспешный вход имеет автора `login-attempt:<заявленное имя>`, а не подтверждённого
  пользователя. Анонимные обращения помечаются `anonymous`.

Триггеры записывают изменение в одной транзакции с бизнес-данными. Если транзакция
откачена, её изменения и соответствующие записи журнала откатываются вместе.
Неуспешный HTTP-запрос при этом остаётся отдельным событием с кодом ошибки.
События обращений API записываются отдельной транзакцией: если сама БД недоступна,
ошибка записи выводится в серверный лог; восстановить такое событие после сбоя
автоматически нельзя. Ошибка транзакционной записи аудита бизнес-изменения не позволяет
успешно сохранить это изменение.

Не записываются тела HTTP-запросов/ответов, заголовки, cookies, query string, пароли,
хеши паролей, токены сессий/ссылок, их хеши и base64 загружаемых файлов. В маршруте
публичной инструкции хранится `{token}`, а не значение секрета. Бизнес-текст документов
и обычные значения полей сохраняются в снимках строк; доступ к журналу поэтому
ограничен администратором.

У журнала нет API удаления или редактирования. UPDATE/DELETE записей запрещены
триггером. Автоматического срока удаления нет; журнал переживает перезапуски и должен
входить в резервные копии PostgreSQL. Это не защита от владельца БД: технический
администратор с соответствующими правами может отключить триггеры или очистить таблицу.
TRUNCATE используется только инфраструктурой изолированных интеграционных тестов.

## Миграция и сопровождение

Миграция `20260906_0015` добавляет журнал и триггеры. В локальной базе разработки
она уже применена. В других окружениях перед запуском новой версии:

```powershell
cd backend
.\.venv\Scripts\alembic upgrade head
```

История начинается после применения миграции. События, произошедшие до неё, не
восстанавливаются. Миграция не изменяет существующие бизнес-записи.

При добавлении новой бизнес-таблицы в будущей миграции нужно подключить триггер:

```sql
CREATE TRIGGER audit_row_change
AFTER INSERT OR UPDATE OR DELETE ON public.new_business_table
FOR EACH ROW EXECUTE FUNCTION public.audit_row_change();
```

Если появятся новые поля с секретами, их нужно исключить из функции аудита отдельной
миграцией. Рост таблицы следует отслеживать вместе с размером резервных копий;
очистка истории не выполняется приложением.

Проверки включают реальную PostgreSQL: расчёт общей закупки, неполные цены, отмену
плана, приход, состав XLSX, фильтры, права, связь запроса с изменением, редактирование
и откат транзакции, защиту журнала от изменения и отсутствие секретов. UI-тесты
проверяют отображение дефицита и раскрытие сохранённых снимков.
