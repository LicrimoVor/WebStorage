# Техническое задание

## Информационная система «Веб-склад»

**Версия:** 1.0  
**Тип системы:** внутренняя веб-система управления производством, складом, технологическими процессами, персоналом и финансами.

---

# 1. Назначение системы

«Веб-склад» предназначен для ведения производственного и складского учета предприятия.

Система должна объединять в одном приложении:

- учет материалов;
- учет полуфабрикатов;
- учет готовой продукции;
- описание технологических процессов;
- расчет потребности в материалах и полуфабрикатах;
- расчет необходимых производственных операций;
- расчет трудозатрат;
- учет выполненных сотрудниками операций;
- расчет задолженности перед сотрудниками;
- учет выплат;
- учет произведенной продукции;
- учет продаж;
- базовый финансовый учет;
- статистику производства, продаж и затрат.

Основная задача системы — после указания требуемого количества конечного продукта автоматически рассчитать всю производственную цепочку:

```text
Продукт
   ↓
Необходимые полуфабрикаты
   ↓
Необходимые материалы
   ↓
Необходимые операции
   ↓
Человеко-часы
   ↓
Стоимость материалов и работ
```

При выполнении производства расчет должен автоматически актуализироваться.

---

# 2. Основные понятия

## 2.1. Материал

Материал — складская сущность, которая приобретается или поступает извне и используется в производстве.

Примеры:

- пластина;
- болт;
- гайка;
- профиль;
- краска;
- провод;
- лист металла.

Материал сам по себе не имеет собственного технологического процесса.

---

# 2.2. Полуфабрикат

Полуфабрикат — складская сущность, которая производится внутри системы из материалов, других полуфабрикатов и производственных операций.

Примеры:

- пластина с креплением;
- сварная рама;
- корпус;
- собранный модуль.

Полуфабрикат может использоваться в других технологических процессах.

---

# 2.3. Продукт

Продукт является частным случаем полуфабриката.

Для полуфабриката существует поле:

```text
is_product: boolean
```

Если `is_product = true`, сущность считается конечным продуктом и может:

- участвовать в производственном плане;
- учитываться как готовая продукция;
- продаваться;
- отображаться в статистике продуктов.

При этом технически продукт остается производимой складской сущностью и может иметь технологический процесс.

---

# 2.4. Операция

Операция — производственное действие.

Примеры:

- сверление;
- резка;
- сварка;
- покраска;
- сборка;
- закручивание;
- шлифовка.

Для операции может быть указана норма времени и стоимость выполнения одной операции.

---

# 2.5. Технологический процесс

Технологический процесс определяет, какие материалы, полуфабрикаты и операции необходимы для изготовления одной единицы полуфабриката или продукта.

Технологический процесс представляется ориентированным графом.

---

# 2.6. Производственный план

Производственный план — задание вида:

```text
Произвести N единиц продукта X
```

На основании производственного плана система автоматически рассчитывает:

- требуемые полуфабрикаты;
- требуемые материалы;
- требуемые операции;
- требуемое время;
- ориентировочную себестоимость;
- дефицит складских остатков.

# 4.2. Планирование производства

Пользователь должен иметь возможность выбрать продукт и указать:

```text
Продукт: Корпус А
Необходимо произвести: 100 шт.
```

После создания производственного плана система выполняет полный расчет технологического дерева.

Для одного продукта могут существовать несколько производственных планов.

Например:

```text
Корпус А       100 шт.
Корпус Б        50 шт.
Модуль C        20 шт.
```

Все потребности должны агрегироваться.

---

# 4.3. Карточка производственного плана

Для каждого плана отображается:

- оставшееся количество;
- дата создания;
- статус;
- используемая версия техпроцесса;
- необходимые материалы;
- необходимые полуфабрикаты;
- необходимые операции;
- расчетные человеко-часы.

Статусы:

```text
Черновик
Активен
Выполнен
Отменен
```

# 5. Логика расчета производства

Это ключевая часть системы.

## 5.1. Пример

Пусть для изготовления одной единицы:

```text
Пластина с креплением
```

необходимо:

```text
Пластина       1 шт.
Шуруп           4 шт.
Сверление      4 операции
Закручивание   4 операции
```

Для изготовления:

```text
Корпус
```

необходимо:

```text
Пластина с креплением    4 шт.
Профиль                   2 шт.
Сварка                    8 операций
```

При плане:

```text
Корпус — 10 шт.
```

система должна рассчитать:

```text
Пластина с креплением: 40 шт.
Профиль:                20 шт.

Пластина:               40 шт.
Шуруп:                  160 шт.

Сверление:              160 операций
Закручивание:           160 операций
Сварка:                  80 операций
```

---

# 5.2. Учет складских остатков

Для материалов и полуфабрикатов необходимо различать минимум три значения:

```text
Свободно
Требуется
Дефицит
```

Где:

```text
Свободно
```

— фактическое доступное количество на складе.

```text
Требуется
```

— расчетная потребность по активным производственным планам.

```text
Дефицит = max(Требуется - Свободно, 0)
```

Для полуфабриката дополнительно вычисляется:

```text
Необходимо произвести =
max(Требуется - Свободно, 0)
```

Расчет материалов и операций нижнего уровня выполняется только для того количества полуфабрикатов, которое действительно необходимо произвести.

---

# 5.3. Учет имеющихся полуфабрикатов

Например:

```text
Для производства необходимо:
Пластина с креплением — 40 шт.

На складе:
Пластина с креплением — 10 шт.
```

Система должна рассчитывать:

```text
Необходимо произвести: 30 шт.
```

Следовательно, материалы и операции для изготовления данного полуфабриката рассчитываются только на 30 единиц.

---

# 5.4. Циклические зависимости

Технологический процесс не должен допускать циклические производственные зависимости.

Например, запрещена ситуация:

```text
A требует B
B требует C
C требует A
```

Система должна выявлять цикл до сохранения или активации технологического процесса.

# 7.4. Изменение количества

```text

Продажа
Корректировка
Списание
```

Интерфейс при этом может выглядеть как обычная кнопка:

```text
Изменить остаток
```

но система должна сохранять историю.

# 9. Производство полуфабрикатов и продуктов

Пользователь должен иметь возможность зарегистрировать факт производства.

Например:

```text
Произведено:
Пластина с креплением — 10 шт.
```

При подтверждении производства система должна создать производственную запись.

Запись содержит:

```text
production_id
production_plan_id
item_id
quantity
process_version_id
created_at
comment
```

После проведения производства:

1. произведенная сущность увеличивается на складе;
2. необходимые компоненты списываются со склада;
3. расчет оставшейся производственной потребности обновляется;
4. необходимое количество операций пересчитывается;
5. производственный план обновляет прогресс.

Для конечного продукта дополнительно увеличивается значение произведенной продукции.

---

# 10. Производственное списание

При производстве система должна рассчитывать нормативное списание согласно выбранной версии техпроцесса.

Например:

```text
Произведено 5 пластин с креплением
```

при норме:

```text
Пластина  1
Шуруп     4
```

создает движения:

```text
Пластина   -5
Шуруп     -20
Пластина с креплением +5
```

При недостаточном количестве компонентов по умолчанию проведение производства блокируется.

Администратор может иметь право выполнить принудительное проведение либо корректировку, если такой режим будет разрешен настройками системы.

# 11. Страница «Операции»

## 11.1. Таблица операций

Для каждой операции отображается:

- название;
- необходимое количество операций;
- норма времени;
- ставка рублей за операцию;
- выполненное количество;
- раскрытие истории выполненных работ;
- действия.

`Необходимое количество` рассчитывается автоматически на основе активных производственных планов и их технологических процессов.

---

# 11.2. Поля операции

```text
id
name
time_norm
price_per_operation
created_at
updated_at
archived
```

`time_norm` — нормативное время выполнения одной операции.

Например:

```text
Сверление
Норма: 3 минуты / операция
Ставка: 12 руб. / операция
```

Оба финансовых параметра могут отсутствовать.

---

# 11.3. Человеко-часы

Если для операции указана норма времени:

```text
Необходимое время =
Количество необходимых операций × Норма времени
```

Общий объем человеко-часов:

```text
Σ необходимого времени всех операций
```

Пример:

```text
Сверление:
160 операций × 3 минуты = 480 минут

Сварка:
80 операций × 10 минут = 800 минут
```

Итого:

```text
1280 минут
21 ч. 20 мин.
```

---

# 11.4. Выполненные операции

Строка операции должна раскрываться.

В подстроках отображаются записи выполненной работы:

| Поле              | Описание                            |
| ----------------- | ----------------------------------- |
| Сотрудник         | ФИО                                 |
| Создано           | дата и время                        |
| Выполнено         | количество операций или время       |
| Начислено         | руб.                                |
| Оплачено          | руб.                                |
| Осталось оплатить | руб.                                |
| Действия          | изменить / удалить при наличии прав |

---

# 11.5. Добавление выполненной операции

Кнопка:

```text
Добавить отработанную операцию
```

Пользователь выбирает:

- сотрудника;
- способ ввода;
- количество операций или затраченное время;
- дату/время выполнения;
- комментарий.

При этом если добавляется или изменяется выполненная операция можно указать, чтобы выполняелся алгоритм Производственное списание.

Разрешено:

- создать новую запись тому же сотруднику;
- изменить предыдущую запись;
- добавить несколько записей одного сотрудника на одну операцию.

---

# 11.6. Способы учета операции

Поддерживается два варианта.

### По количеству

Пользователь вводит:

```text
20 операций
```

Начисление:

```text
20 × ставка
```

### По времени

Пользователь вводит:

```text
60 минут
```

Если норма составляет:

```text
3 минуты / операция
```

эквивалентное количество:

```text
60 / 3 = 20 операций
```

Начисление:

```text
20 × ставка
```

Если ставка или необходимая норма отсутствует, система показывает, что автоматический расчет оплаты невозможен.

---

# 11.7. Фиксация ставки

При создании записи выполненной операции необходимо сохранять ставку на этот момент.

Например:

```text
01.05 ставка = 10 руб.
01.06 ставка изменена = 15 руб.
```

Работы за май должны продолжать рассчитываться исходя из ставки 10 руб.

Изменение текущей ставки операции не должно изменять исторические начисления.

# 13. Оплата персонала

Выплата сотруднику должна являться отдельной финансовой операцией.

Сущность выплаты:

```text
payment_id
employee_id
amount
paid_at
comment
created_at
```

Необходимо хранить распределение выплаты по начислениям.

Это позволяет корректно определить поле:

```text
Оплачено
```

для каждой записи выполненной операции.

По умолчанию допускается автоматически распределять оплату от старых неоплаченных работ к новым.

Также должна существовать возможность ручного распределения.

Расчет:

```text
К оплате =
Σ начислений - Σ выплат
```

# 14. Страница «Технологические процессы»

Страница состоит из:

2. редактора конкретного технологического процесса.

---

# 15. Список технологических процессов

Для каждого процесса показывается:

- название;
- производимый полуфабрикат/продукт;
- версия;
- статус;
- дата изменения;
- автор изменения;
- действия.

Статусы:

```text
Черновик
Активный
Архивный
```

Для одного продукта могут существовать несколько версий технологического процесса, но только одна версия должна быть активной.

---

# 16. Версионирование техпроцессов

Изменение действующего техпроцесса не должно изменять историю уже выполненного производства.

Поэтому при существенном редактировании создается новая версия.

Например:

```text
Корпус A
v1 — архивная
v2 — активная
```

Производственный план должен знать, по какой версии он рассчитывался.

Изменение активной версии не должно молча пересчитывать уже существующий активный план.

Для такого плана должна быть отдельная команда:

```text
Пересчитать по новой версии
```

# 17. Редактор технологического процесса

Основная область страницы представляет собой Canvas с карточками-узлами и соединениями.

Типы узлов:

```text
Материал

Операция
Продукт
```

Карточка должна визуально показывать тип.

Поля:

Полуфабрикат может иметь собственный технологический процесс.

# 21. Соединения графа

Соединение означает:

```text
Источник необходим для изготовления назначения
```

Например:

```text
Пластина ────────┐
                 │
Шуруп ───────────┼──> Пластина с креплением
                 │
Сверление ───────┤
                 │
Закручивание ────┘
```

Количество концептуально принадлежит зависимости между компонентом и производимой сущностью.

В интерфейсе оно может отображаться непосредственно внутри карточки.

Если один и тот же материал используется в нескольких местах процесса, допускается создать несколько визуальных узлов, ссылающихся на одну складскую сущность.

При расчете требования агрегируются.

# 24. Валидация техпроцесса

Перед активацией система должна проверить:

- указан конечный результат;
- все узлы сопоставлены существующим сущностям;
- количество больше нуля;
- отсутствуют циклы;
- отсутствуют битые соединения;
- каждая производимая сущность имеет корректную цепочку;
- не используются архивированные сущности;
- для продукта определен конечный узел.

Процесс с ошибками разрешено сохранять как черновик, но нельзя активировать.

# 25. Импорт технологического процесса

Поддерживается частичный импорт.

Форматы:

```text
JSON
Excalidraw
```

Импорт не обязан быть полностью заполненным.

Например, из файла могут быть получены:

- названия;
- расположение блоков;
- соединения;
- текстовые значения.

После импорта пользователь должен иметь возможность вручную:

- выбрать тип узла;
- сопоставить узел существующему материалу;
- сопоставить узел полуфабрикату;
- сопоставить узел операции;
- указать количество;
- исправить соединения.

До завершения сопоставления процесс сохраняется со статусом:

```text
Черновик
```

# 26. JSON-формат техпроцесса

Внутренний JSON должен иметь версионируемую схему.

Пример концепции:

```json
{
	"schemaVersion": 1,
	"name": "Корпус A",
	"outputItemId": "product-id",
	"nodes": [
		{
			"id": "node-1",
			"type": "material",
			"referenceId": "material-id",
			"position": {
				"x": 100,
				"y": 200
			}
		}
	],
	"edges": [
		{
			"id": "edge-1",
			"source": "node-1",
			"target": "node-5",
			"quantity": "4"
		}
	]
}
```

Количество передается в точном числовом формате без потери decimal precision.

# 27. Excalidraw

Необходимо поддерживать:

```text
Экспорт в .excalidraw
Импорт из .excalidraw
```

Экспортированный самой системой Excalidraw-файл должен по возможности повторно импортироваться без потери связей с доменными сущностями.

Для произвольного Excalidraw-файла допускается частичный импорт:

- прямоугольники и текст преобразуются в черновые узлы;
- стрелки — в связи;
- неизвестные элементы игнорируются либо сохраняются как декоративные;
- пользователь вручную завершает сопоставление.

# 32. Расчет ориентировочной себестоимости

При наличии цен материалов и ставок операций система может рассчитывать нормативную себестоимость.

```text
Себестоимость =
материалы +
операции
```

Материалы:

```text
Σ количество × цена
```

Операции:

```text
Σ количество операций × ставка
```

Если часть цен отсутствует, результат помечается как:

```text
Неполный расчет
```

и система показывает отсутствующие исходные данные.

# 57. Основные критерии приемки

Система считается функционально готовой к первой эксплуатации, если выполняется следующий сквозной сценарий.

### Шаг 1

Пользователь создает:

```text
Материал: Пластина
Материал: Шуруп
```

### Шаг 2

Создает операции:

```text
Сверление
Закручивание
```

### Шаг 3

Создает полуфабрикат:

```text
Пластина с креплением
```

### Шаг 4

В Canvas создает техпроцесс:

```text
1 Пластина
4 Шурупа
4 Сверления
4 Закручивания
      ↓
1 Пластина с креплением
```

### Шаг 5

Создает конечный продукт:

```text
Корпус
```

и технологический процесс:

```text
4 Пластины с креплением
2 Профиля
8 операций сварки
      ↓
1 Корпус
```

### Шаг 6

Создает производственный план:

```text
10 Корпусов
```

### Шаг 7

Система автоматически рассчитывает все необходимые:

```text
материалы
полуфабрикаты
операции
человеко-часы
```

с учетом складских остатков.

### Шаг 8

Пользователь регистрирует производство полуфабрикатов.

Система:

- добавляет их на склад;
- списывает материалы;
- пересчитывает оставшуюся потребность.

### Шаг 9

Сотрудник выполняет операцию.

Пользователь регистрирует:

```text
Иванов Иван Иванович
Сверление
20 операций
```

Система рассчитывает начисление.

### Шаг 10

Пользователю можно зарегистрировать выплату сотруднику.

После выплаты корректно изменяются:

```text
Оплачено
Необходимо оплатить
```

### Шаг 11

Пользователь регистрирует изготовление конечного продукта.

Продукт появляется на складе.

Производственный план обновляется.

### Шаг 12

Пользователь регистрирует продажу продукта.

Количество продукта на складе уменьшается.

### Шаг 13

Аналитика отображает:

```text
сколько произведено
сколько продано
остатки
начисления
выплаты
выручку
человеко-часы
```

# 58. Важные бизнес-правила

1. `Требуемое количество` никогда не вводится вручную — оно вычисляется системой.
2. Складские остатки изменяются через движения.
3. Любой произведенный полуфабрикат является полноценной складской единицей.
4. Продукт является производимой складской единицей с признаком `is_product`.
5. Один полуфабрикат может входить в любое количество других техпроцессов.
6. Один материал может использоваться во множестве процессов.
7. Одна операция может использоваться во множестве процессов.
8. Техпроцессы не могут содержать циклических зависимостей.
9. Исторические производственные записи привязаны к конкретной версии техпроцесса.
10. Изменение текущей стоимости операции не изменяет историческое начисление сотруднику.
11. Изменение текущей цены материала не должно менять зафиксированные исторические финансовые операции.
12. Backend является источником истины для производственных расчетов.
13. Frontend не должен самостоятельно пересчитывать критичные производственные данные независимо от backend.
14. Все финансовые и складские операции должны оставлять историю.
15. Архивирование предпочтительнее физического удаления сущностей, участвовавших в учете.

# 59. Рабочие предположения первой версии

На первом этапе принимаются следующие решения:

- используется один физический склад;
- резервирование товара отдельно от свободного остатка пока отсутствует;
- валюта системы — RUB;
- продукт технически является полуфабрикатом с `is_product = true`;
- один продукт может иметь несколько версий техпроцесса;
- одновременно активна одна версия;
- производственный план фиксирует используемую версию;
- факт выполненной сотрудником операции используется для учета труда и оплаты;
- производственный остаток потребности уменьшается фактом производства полуфабриката/продукта, а не только фактом создания сотрудником записи о работе;
- отрицательные складские остатки по умолчанию запрещены;
- ручная корректировка остатков разрешена, но всегда записывается в журнал движений.

# 60. Экспорт таблиц в Excel

Для основных табличных разделов системы необходимо предусмотреть экспорт данных в формат Excel (`.xlsx`).

Экспорт должен быть доступен минимум для следующих разделов:

- материалы;
- полуфабрикаты и продукты;
- складские движения;
- операции;
- выполненные операции;
- персонал;
- начисления сотрудникам;
- выплаты сотрудникам;
- производственные планы;
- производство;
- продажи;
- финансовые операции;
- аналитические таблицы.

Экспорт должен учитывать текущие параметры отображения таблицы:

- примененные фильтры;
- поисковый запрос;
- выбранный период;
- сортировку;
- выбранный продукт;
- выбранного сотрудника;
- выбранную операцию;
- другие активные фильтры конкретного раздела.

По умолчанию экспортируется весь набор данных, соответствующий текущим фильтрам, а не только текущая страница пагинации.

Необходимо предусмотреть возможность экспорта:

```text
Экспортировать все найденные записи
```

и, если в таблице реализован множественный выбор:

```text
Экспортировать выбранные записи
```

Excel-файл должен содержать человекочитаемые значения вместо внутренних идентификаторов.

Например, вместо:

```text
employee_id = 1d8f...
operation_id = 7ac4...
```

необходимо выводить:

```text
Сотрудник: Иванов Иван Иванович
Операция: Сверление
```

Даты, денежные значения и количества должны записываться в Excel в соответствующих типах ячеек, чтобы пользователь мог выполнять дальнейшие вычисления, сортировку и фильтрацию средствами Excel.

Для денежных колонок необходимо использовать числовой формат.

Для дат — формат даты/времени.

Для количеств необходимо сохранять исходную decimal-точность.

Название экспортируемого файла должно содержать тип данных и дату формирования.

Примеры:

```text
materials_2026-08-28.xlsx
employees_2026-08-28.xlsx
sales_2026-08-01_2026-08-28.xlsx
inventory_movements_2026-08-28.xlsx
```

Формирование больших файлов должно выполняться на backend.

Frontend не должен загружать десятки тысяч строк только для последующей генерации Excel-файла в браузере.

# 61. Инструкция по выполнению операции

Для каждой производственной операции необходимо предусмотреть отдельную инструкцию для сотрудника.

Например:

```text
Операция:
Сверление отверстий корпуса

Инструкция:
как установить деталь;
каким сверлом пользоваться;
где расположены отверстия;
какая допустимая погрешность;
как проверить результат;
требования безопасности.
```

Инструкция является отдельным документом, связанным с операцией.

---

## 61.1. Формат инструкции

Основным исходным форматом инструкции является Markdown.

Инструкция должна поддерживать:

- заголовки;
- обычный текст;
- жирный текст;
- курсив;
- списки;
- нумерованные списки;
- таблицы;
- ссылки;
- изображения;
- цитаты;
- блоки кода;
- разделители.

Пример:

```md
# Сверление крепежных отверстий

## Необходимый инструмент

- сверлильный станок;
- сверло Ø5 мм;
- защитные очки.

## Порядок работы

1. Установить деталь согласно схеме.
2. Зафиксировать деталь.
3. Проверить размер.
4. Выполнить четыре отверстия.

![Схема установки](./images/drilling-position.png)

> Перед началом работы убедиться в надежной фиксации детали.

## Контроль результата

Допустимое отклонение расположения отверстия: ±0.5 мм.
```

---

# 61.2. Изображения

В Markdown-инструкцию должна существовать возможность загружать изображения.

Изображения хранятся системой и вставляются в документ.

Пользователь должен иметь возможность:

- загрузить изображение;
- вставить его в необходимое место документа;
- заменить изображение;
- удалить изображение;
- указать подпись;
- открыть изображение в увеличенном виде.

При удалении инструкции или изображения необходимо учитывать существующие версии документа и публичные ссылки.

---

# 61.3. Редактор инструкции

Для редактирования необходимо предоставить Markdown-редактор.

Желательный режим:

```text
Редактор | Предпросмотр
```

либо:

```text
Markdown
+
Live Preview
```

Пользователь должен видеть результат приблизительно в том виде, в котором его увидит сотрудник.

Необходимо поддержать:

- автосохранение черновика;
- явную кнопку сохранения;
- отображение статуса сохранения;
- вставку изображений;
- drag-and-drop изображений, если это поддерживает выбранный редактор;
- вставку изображения из буфера обмена.

---

# 61.4. Отдельная страница инструкции

У каждой операции должна существовать отдельная страница инструкции.

Пример маршрута:

```text
/operations/:operationId/instruction
```

Страница должна отображать:

- название операции;
- актуальную инструкцию;
- изображения;
- дату последнего изменения;
- действия для пользователя с правами редактирования.

Пример:

```text
Сверление

Инструкция по выполнению операции

[содержимое Markdown]

Последнее изменение:
28.08.2026 14:25
```

---

# 61.5. Связь со страницей операций

В таблице операций необходимо добавить действие:

```text
Открыть инструкцию
```

Если инструкция отсутствует:

```text
Создать инструкцию
```

При добавлении записи выполненной операции также желательно предоставить быстрый доступ к инструкции.

Это позволит сотруднику открыть технологические требования непосредственно перед выполнением работы.

---

# 61.6. Экспорт инструкции

Инструкцию конкретной операции необходимо иметь возможность выгрузить в следующих форматах:

```text
.txt
.md
.docx
.pdf
```

### Markdown

Файл `.md` должен содержать исходный Markdown инструкции.

Изображения при необходимости могут экспортироваться вместе с документом отдельными файлами либо упаковываться в архив с сохранением относительных ссылок.

### TXT

Файл `.txt` содержит текстовое представление инструкции без Markdown-разметки.

### Word

Файл `.docx` должен сохранять:

- заголовки;
- списки;
- таблицы;
- изображения;
- форматирование текста.

### PDF

PDF должен представлять собой готовую для просмотра и печати инструкцию.

PDF должен содержать:

- название операции;
- инструкцию;
- изображения;
- дату формирования документа.

При необходимости в дальнейшем может быть добавлен:

- логотип организации;
- номер документа;
- версия;
- подпись ответственного;
- QR-код на актуальную онлайн-версию.

---

# 61.7. Публичная ссылка

Для инструкции должна существовать возможность создать публичную ссылку.

Пример:

```text
https://warehouse.example.com/public/instructions/AbCDef123...
```

Открытие публичной инструкции не должно требовать авторизации в основной системе.

Публичная страница должна предоставлять только доступ к самой инструкции.

Через публичную страницу нельзя получать доступ:

- к складу;
- к сотрудникам;
- к финансам;
- к производственным планам;
- к другим внутренним данным системы.

Публичная ссылка должна использовать случайный криптографически стойкий идентификатор, который невозможно практически подобрать перебором.

---

# 61.8. Управление публичной ссылкой

Пользователь с соответствующими правами должен иметь возможность:

```text
Создать публичную ссылку
Скопировать ссылку
Отключить ссылку
Создать новую ссылку
```

При создании ссылки желательно позволить выбрать срок действия:

```text
Без ограничения
1 день
7 дней
30 дней
До указанной даты
```

После отключения ссылка должна перестать работать.

При генерации новой ссылки старая ссылка может быть автоматически отозвана.

---

# 61.9. Публичное представление

Публичная страница должна быть максимально простой и подходящей для использования сотрудником непосредственно на рабочем месте.

Она должна содержать:

```text
Название операции

Описание / инструкция

Изображения

Дата или версия инструкции
```

Страница должна корректно работать:

- на компьютере;
- на планшете;
- на смартфоне.

Для производственного использования особенно важна удобная мобильная верстка.

Публичную страницу желательно сделать пригодной для печати непосредственно из браузера.

---

# 61.10. QR-код

Для публичной ссылки желательно автоматически генерировать QR-код.

QR-код можно:

- открыть;
- скачать;
- распечатать.

Это позволит разместить QR-код непосредственно:

- возле рабочего места;
- на станке;
- на производственном участке;
- в бумажной технологической карте.

Сотрудник сможет отсканировать QR-код телефоном и сразу открыть актуальную инструкцию.

---

# 61.11. Версионирование инструкции

Изменение инструкции не должно приводить к потере предыдущей версии.

Необходимо предусмотреть историю версий.

Минимально для версии сохраняется:

```text
id
operation_id
version
content
created_at
created_by
```

Например:

```text
Сверление

v1 — 01.08.2026
v2 — 15.08.2026
v3 — 28.08.2026 — текущая
```

Для обычного просмотра показывается актуальная версия.

Пользователь с необходимыми правами должен иметь возможность посмотреть историю изменений.

---

# 61.12. Поведение публичной ссылки при изменении инструкции

По умолчанию публичная ссылка операции должна вести на актуальную опубликованную версию инструкции.

Таким образом, если QR-код уже распечатан и размещен на рабочем месте, после обновления инструкции не требуется печатать новый QR-код.

При этом необходимо различать:

```text
Черновик
Опубликованная версия
```

Изменение черновика не должно сразу менять публичную инструкцию.

Обновление публичной версии происходит после команды:

```text
Опубликовать
```

Это предотвращает ситуацию, когда сотрудник увидит частично отредактированную инструкцию.

---

# 61.13. Статусы инструкции

Инструкция может иметь состояния:

```text
Отсутствует
Черновик
Опубликована
```

При редактировании опубликованной инструкции создается новый черновик.

До его публикации сотрудникам продолжает отображаться предыдущая опубликованная версия.

---

# 61.14. Безопасность Markdown

Markdown должен преобразовываться в безопасный HTML.

Необходимо предотвращать выполнение пользовательского JavaScript и потенциально опасного HTML.

Запрещено напрямую рендерить непроверенный HTML из Markdown.

Необходимо предусмотреть защиту от XSS.

---

# 61.15. Права доступа

Минимально:

### Просмотр

Пользователи производства могут просматривать опубликованную инструкцию.

### Редактирование

Редактировать инструкцию могут только пользователи с соответствующим разрешением.

### Публикация

Публикация новой версии может быть отдельным разрешением.

### Публичные ссылки

Создание и отзыв публичных ссылок также должны контролироваться разрешениями.

---

# 61.16. Основные критерии приемки инструкции

Функция считается реализованной, если выполняется следующий сценарий:

1. Пользователь открывает операцию `Сверление`.
2. Создает инструкцию.
3. Добавляет Markdown-текст.
4. Загружает несколько изображений.
5. Сохраняет черновик.
6. Публикует инструкцию.
7. Открывает ее отдельную страницу.
8. Выгружает инструкцию в `.md`.
9. Выгружает инструкцию в `.txt`.
10. Выгружает инструкцию в `.docx`.
11. Выгружает инструкцию в `.pdf`.
12. Создает публичную ссылку.
